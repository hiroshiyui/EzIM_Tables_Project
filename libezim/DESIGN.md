# libezim — Design Document

A Rust implementation of the 輕鬆輸入法 (EZ) input method engine, exposing a stable C ABI so it can be embedded by IME frameworks (IBus, Fcitx5, macOS InputMethodKit, Windows TSF, etc.) and other languages via FFI. Inspired by the architecture of `libchewing`.

Status: **draft for review** — no code yet.

---

## 1. Goals

1. **Correct EZ encoding/decoding.** Faithfully implement the取碼規則 documented in the project's `CLAUDE.md`:
   - Per-character head/tail selection (single-key preferred, avoid all-numeric, file order).
   - Word-length-dependent取碼 (1 char → 2 codes, 2 chars → 4 codes, 3 chars → 3 codes, 4 chars → 4 codes, ≥5 chars → 4 codes).
2. **Stable C ABI** suitable for binding from C, C++, Python (cffi), Node, Go, etc.
3. **Phased delivery**: ship a usable lookup-only core first; add session/state on top.
4. **Pre-built binary table** for fast startup, mmap-friendly, version-stamped.
5. **Memory safety**: no `unsafe` outside the FFI boundary crate.
6. **Cross-platform**: Linux (primary), macOS, Windows.

### Non-goals (initial)

- GUI / candidate window rendering — that belongs in the IME framework integration.
- Cloud lookup, prediction, ML reordering.
- User dictionary editing UI (the API will support it; the UI does not).

## 2. Reference: how `libchewing` is shaped

Useful prior art to mirror selectively:

| libchewing concept | libezim analogue |
| --- | --- |
| `chewing_new()` / `ChewingContext *` | `ezim_context_new()` / opaque `EzimContext *` |
| Bopomofo keystroke buffer | EZ key-code buffer (a–z, `'`, `,`, `.`, `;`, `\``, digits) |
| `chewing_handle_*` per key | `ezim_handle_key(ctx, key)` |
| `chewing_buffer_String` (committed) | `ezim_commit_string()` |
| `chewing_cand_*` (candidate paging) | `ezim_cand_*` |
| `.dat` data files (`tsi.dat`, `word.dat`) | `ez.dat` (binary table) + optional `ezbig.dat`, `ezmid.dat`, `ezsmall.dat` |
| User phrase DB (sqlite) | User dictionary (sqlite or simple binary) |

Key differences from chewing:
- **EZ取碼 is deterministic given a string**, so encoding is a *function*, not a search. Lookup is the inverse direction (code → candidate words). This simplifies the core dramatically.
- **Multiple codes per character** (e.g. `七 → ["76", "j'", "m'"]`) means the table is many-to-many; selection rules pick the canonical one.

Phases:
- **Phase 1**: `ezim-core` + `ezim-table-builder` + `ezim-cli`. Rust-only, no FFI. Validates encoding rules end-to-end against `ez.orig-utf8.txt`.
- **Phase 2**: `ezim-capi` exposing core (load table, encode string → codes, lookup code → candidates). Generate `ezim.h`. Add a small `tests/c/` smoke test compiled with the system C compiler.
- **Phase 3**: `ezim-session` + extend C API with session functions (`ezim_session_*`).
- **Phase 4**: User dictionary, persistence.

## 4. Binary table format (`ez.dat`)

Goals: mmap-able, endian-defined (little-endian on disk), versioned, deterministic, fast lookup in both directions.

```
Header (64 bytes, fixed)
  magic       : "EZIMTBL\0"          (8 B)
  version     : u32                   (major.minor packed)
  flags       : u32                   (bit 0: has_phrase_index)
  source_hash : [u8; 32]              (SHA-256 of source .txt — for cache invalidation)
  n_entries   : u32
  n_chars     : u32                   (distinct chars/phrases)
  reserved    : [u8; ...]

Section 1 — String pool
  All char/phrase strings, UTF-8, NUL-terminated, sorted unique.
  Entries elsewhere reference these by 32-bit byte-offset.

Section 2 — Code pool
  All code strings (ASCII, ≤ ~6 bytes), NUL-terminated.

Section 3 — Entries (sorted by code, stable)
  struct Entry {
    code_off    : u32   // into Code pool
    string_off  : u32   // into String pool
    flags       : u16   // bit 0: is_phrase, bit 1: all_numeric_code
    code_len    : u8
    str_charlen : u8    // # of Unicode scalar values (1=char, ≥2=phrase)
  }                     // 12 bytes, naturally aligned

Section 4 — Code index (perfect hash or sorted array + binary search)
  For code → entries lookup. Start with sorted-array + bsearch; revisit if profiling demands.

Section 5 — Char index
  Sorted by string_off (or by (char, code_len, code_off)) so that for any char
  we can enumerate its codes in original file order. Required to implement the
  head/tail selection rule deterministically.
```

Notes:
- The builder preserves **original file order** for the char-index, since rule #3 ("依檔案排列順序") depends on it.
- `flags::all_numeric_code` is precomputed so the picker doesn't re-scan ASCII at runtime.
- mmap is the default load path; an "owned buffer" path stays available for environments without mmap (Windows native, embedded).

## 5. Encoding API (`ezim-core`)

```rust
pub struct Table { /* mmap-backed or Vec-backed */ }

impl Table {
    pub fn open<P: AsRef<Path>>(path: P) -> Result<Self, Error>;
    pub fn from_bytes(buf: Cow<'_, [u8]>) -> Result<Self, Error>;

    /// Pick the canonical (head, tail) codes for a single character per CLAUDE.md rules.
    pub fn pick_codes(&self, ch: char) -> Option<(Code<'_>, Code<'_>)>;

    /// Encode a string per word-length rules. Returns the EZ code sequence.
    pub fn encode(&self, s: &str) -> Result<String, EncodeError>;

    /// Reverse lookup: given a code, list candidate strings (chars or phrases) in table order.
    pub fn lookup<'a>(&'a self, code: &str) -> CandidateIter<'a>;

    /// Prefix lookup for incremental keystroke matching.
    pub fn lookup_prefix<'a>(&'a self, code_prefix: &str) -> CandidateIter<'a>;
}
```

The picker (`pick_codes`) implements:

```
1. Among entries for `ch`, prefer code with len == 1.
2. Else prefer code where !all_numeric.
3. Else first in original file order.
```

Returned as `(head, tail)` where head = first char of selected code, tail = last char (or the whole code for single-key entries — TBD; CLAUDE.md uses "頭" and "尾" of the picked code, e.g. for `j'` head is `j`).

> **Open question**: for a 2-char code like `j'`, is the "頭" `j` and the "尾" `'`? The CLAUDE.md example for `七 → j'` taking `j` as head supports this. Confirm with the user before locking semantics.

## 6. Session API (`ezim-session`, phase 3)

State machine sketch:

```
[Idle] --key--> [Composing(buf)] --space/enter--> [Selecting(cands)]
   ^                                                     |
   |---commit--- (chosen candidate or auto-commit) <-----+
```

```rust
pub struct Session<'t> {
    table: &'t Table,
    user_dict: Option<&'t UserDict>,
    buffer: KeyBuffer,           // raw keys typed
    preedit: String,             // shown to user
    candidates: Vec<CandRef<'t>>,
    page: usize,
    page_size: usize,            // configurable, default 9
}

impl<'t> Session<'t> {
    pub fn handle_key(&mut self, k: Key) -> StepOutcome;
    pub fn commit(&mut self, idx: Option<usize>) -> Option<String>;
    pub fn cancel(&mut self);
    pub fn page_next(&mut self);
    pub fn page_prev(&mut self);
}
```

`StepOutcome` reports whether the host should redraw preedit, candidates, or pull a commit string.

## 7. C ABI (`ezim-capi`)

### Conventions

- **Opaque handles**: `EzimTable`, `EzimSession` are forward-declared structs. Callers only ever hold pointers.
- **Strings in**: `const char *` UTF-8, NUL-terminated, caller-owned.
- **Strings out**: returned as `const char *` valid until the next call on the same handle, OR allocated and freed via `ezim_string_free()`. Be consistent — pick the `_free` model for anything the caller may want to retain.
- **Errors**: every fallible function returns `EzimStatus` (an `int32_t`). Out-params for results. A thread-local "last error message" retrievable via `ezim_last_error()`.
- **Versioning**: `ezim_version_string()`, `ezim_abi_version()` returning a u32. Major bump = breaking ABI.
- **Thread safety**: `EzimTable` is `Send + Sync` (read-only after load). `EzimSession` is `Send` but **not** `Sync` — caller must not share without external locking. Documented in the header.

### Phase 2 surface (lookup)

```c
typedef struct EzimTable EzimTable;
typedef int32_t EzimStatus;

#define EZIM_OK            0
#define EZIM_ERR_IO       -1
#define EZIM_ERR_FORMAT   -2
#define EZIM_ERR_NOT_FOUND -3
#define EZIM_ERR_INVALID  -4
/* ... */

uint32_t      ezim_abi_version(void);
const char *  ezim_version_string(void);
const char *  ezim_last_error(void);

EzimStatus    ezim_table_open(const char *path, EzimTable **out);
void          ezim_table_free(EzimTable *t);

/* Encode a UTF-8 string into its EZ code sequence. *out must be freed. */
EzimStatus    ezim_encode(const EzimTable *t, const char *utf8,
                          char **out_codes);

/* Look up candidates for a code. Returns an iterator handle. */
typedef struct EzimCandIter EzimCandIter;
EzimStatus    ezim_lookup(const EzimTable *t, const char *code,
                          EzimCandIter **out);
const char *  ezim_cand_next(EzimCandIter *it);   /* NULL when done */
void          ezim_cand_free(EzimCandIter *it);

void          ezim_string_free(char *s);
```

### Phase 3 surface (session) — sketch only

```c
typedef struct EzimSession EzimSession;
EzimStatus    ezim_session_new(const EzimTable *t, EzimSession **out);
```

## 8. Data sources & build pipeline

```
ez.orig-utf8.txt  ──┐
ezbig.orig-utf8.txt ┼──> ezim-table-builder ──> ez.dat / ezbig.dat / ...
ezmid.orig-utf8.txt ┤
ezsmall.orig-utf8.txt ┘
```

- The builder is invoked manually (or via `cargo xtask build-tables`). Output `.dat` files are not checked in; instead a Make target / CI step regenerates them, and a checksum is recorded in the crate.
- Source files live at `ezsource12-3/origtable/` (existing). The builder accepts `--source <path>` and `--out <path>`.
- The text format parsed: `code\tstring\n` (verified — see `head` of `ez.orig-utf8.txt`). Lines are processed in file order; that order is preserved in the char-index for rule #3.

## 9. Missing-character推理

CLAUDE.md describes a structural-decomposition推理 procedure for chars not in the table. That is **out of scope** for libezim's runtime — it is an authoring-time aid for editing `ez.orig-utf8.txt`. We will not bake it into the runtime engine.

A separate `ezim-author` tool (later, optional) could scaffold this as an interactive helper.

## 10. Testing strategy

1. **Unit tests** in `ezim-core`:
   - Picker: every example in CLAUDE.md (`一→m`, `七→j'`, `八→8`, `公→8/`) as a parametrised test.
   - End-to-end: `「八一七公報」 → "8mj8"` exactly as documented.
2. **Round-trip fuzzing**: sample N strings from the table, encode them, assert the encoded form prefix-matches a candidate that includes the original.
3. **Golden file**: snapshot encodings of the first 1000 phrases in `ezphrase.txt` (after license-text skip).
4. **C ABI smoke test**: a tiny `.c` program in `crates/ezim-capi/tests/c/smoke.c` compiled in CI with both gcc and clang, linking against the cdylib.
5. **Cross-language sanity**: a Python `ctypes` script in `examples/` to catch ABI accidents early.

## 11. Build, packaging, distribution

- `cargo build -p ezim-capi --release` produces both `libezim.so`/`.dylib`/`.dll` (cdylib) and `libezim.a` (staticlib).
- `pkg-config` `.pc` file installed alongside the cdylib.
- Distro packaging targets (later): Debian, Arch AUR, Homebrew.
- SemVer: ABI compatibility tracked via `ezim_abi_version()`. Header includes `#define EZIM_ABI_VERSION_REQUIRED N` so callers can `static_assert` at compile time.

## 12. Decisions & remaining questions

### Decided (2026-05-08)

1. **"頭" / "尾" semantics**: for a multi-key code like `j'`, head = `j` (first key), tail = `'` (last key). Single-key codes have head == tail.
2. **Tables in scope**: **only `ez.orig-utf8.txt`** (with this project's rearrangements). `ezbig` / `ezmid` / `ezsmall` are out of scope for libezim. The builder takes a single source file; no `--variant` flag.
3. **License**: **GPL-3.0**, to respect the original author's intent. This means any host linking libezim must be GPL-compatible — documented prominently in README. No dual-licensing.

### Decided (continued)

4. **User dictionary format**: **simple binary file** (no sqlite dependency). Same general approach as `ez.dat` — versioned header, string pool, entries — but writable and append-friendly. Concrete layout deferred to M6.
5. **Edition / MSRV**: **Rust 2024 edition** (stabilised in 1.85). MSRV pinned at the minimum stable that supports edition 2024.
6. **Crate name on crates.io**: **`libezim`** (matches the C library name; the workspace internal crates remain `ezim-core`, `ezim-capi`, etc., re-exported from `libezim`).
